# 面试与汇报复盘助手：项目构想、竞争分析与执行分工

- 文档状态：讨论稿 v0.1
- 整理日期：2026-11-15
- 项目周期：2 周 MVP
- 执行方式：单人开发
- 暂定方向：面向面试者、项目答辩者和汇报者的“问题错题本”
- 一句话定位：不替你回答，而是把每次真实问答变成可以复习、重答和追踪的个人问题资产。

---

## 1. 项目摘要

### 1.1 要解决的问题

面试、项目答辩、论文答辩和比赛路演结束后，用户通常会经历以下情况：

- 当时被问了很多问题，事后只记得少数几个。
- 知道自己答得不好，但说不清具体缺了什么。
- 评审的追问往往暴露真正的问题，但追问链没有被保存。
- 用户会把录音转成文字，再复制给通用 AI 分析一次。
- 分析结果通常停留在一次性的总结，没有进入下一次练习。
- 多次面试之间的问题模式没有被比较，导致同类错误反复出现。

### 1.2 产品方案

产品把一次面试或汇报拆成若干个“问题卡”，每张卡包含：

- 原始问题和追问链。
- 可能的考察点和判断依据。
- 用户当时的回答摘要。
- 回答中缺失的证据、结构或边界。
- 用户事后的语音反思。
- 下一次回答的骨架。
- 复习状态和重答记录。

产品最终沉淀的不是会议纪要，而是用户的个人问题库、证据库和高频弱点图谱。

### 1.3 目标用户

第一版优先场景：

- 应届生和在校生。
- 需要讲清楚自己的软件项目、课程项目或比赛项目的人。
- 需要应对老师、评审、导师和同学追问的人。
- 正在准备研发岗位面试、但还缺少项目表达训练的人。

首版不直接服务所有求职者，而是先服务“学生如何讲清楚自己的软件项目”这一件事。

后续扩展方向：

- 校招和社招研发岗位面试。
- 产品、运营、咨询等需要方案表达的岗位。
- 比赛路演和论文答辩。
- 企业内部技术评审和项目复盘。

单人开发时只选择一个主场景，避免同时为多类用户设计不同的评价体系。

### 1.4 成功标准

第一版不以“功能很多”为成功标准，而以以下结果衡量：

- 用户能在 3 分钟内完成一次录音或文字导入。
- 系统能提取出完整的问题和追问链。
- 每个问题都能关联到回答缺口和证据缺口。
- 用户能在一周内重新回答至少 3 个问题。
- 系统能指出跨场次重复出现的问题。
- 相比“复制转写文本给通用 AI”，产品能节省整理时间并产生可追踪的复习记录。
- 单场复盘的模型调用次数和费用可统计，长期使用成本可控。

## 2. 关键竞争问题：为什么不直接复制给 AI

### 2.1 先承认基线方案很强

“语音转文字，复制给 AI，让 AI 总结问题和回答”，这个方案确实有效。

它的优点是：

- 成本低。
- 上手快。
- 通用模型已经具备很强的总结和推理能力。
- 用户不需要安装新产品。
- 对单次面试的即时分析已经足够有用。

因此，如果项目只是：

- 录音。
- 转写。
- 让 AI 总结问题。
- 生成一份复盘报告。

那么这个项目很容易被老师现有的实时评审系统覆盖，也容易被通用 AI 加一段提示词替代。

### 2.2 但“一次性分析”不等于“长期复盘”

复制给通用 AI 的主要限制不在模型能力，而在工作流：

- 用户需要自己选择录音、裁剪内容、复制文本和组织提示词。
- 每次分析都是孤立会话，用户需要自己保存和整理结果。
- 通用 AI 不会自动维护问题卡、追问链、证据库和复习状态。
- 用户很难判断本次问题是否在之前出现过。
- 用户很难看到“我三个月来一直卡在个人贡献和风险边界”这类跨场次模式。
- 用户不会因为一次总结自动进入重答和复习。

更准确地说：

> 长上下文不等于长期记忆。长期复盘需要显式的数据结构、状态管理和复习机制。

### 2.3 个人数据库也不是天然护城河

把文字全部放进自己的数据库，只有存储价值，不等于产品价值。

如果只是保存原始转写，用户会得到一个越来越大的“资料堆”，仍然需要：

- 自己判断哪些内容是问题。
- 自己切分问题和回答。
- 自己给问题分类。
- 自己关联同一类问题。
- 自己决定什么时候复习。
- 自己比较多次表现。

数据库是基础设施，不是产品本身。真正有价值的是：

- 问题如何被结构化。
- 问题如何与证据和回答缺口关联。
- 系统如何发现重复模式。
- 系统如何把分析转成下一次训练动作。

### 2.4 与老师网站的关系

从提供的页面可以看出，老师网站更偏向：

- 汇报前的练习。
- 汇报过程中的实时语音识别。
- AI 评审实时打断和追问。
- 教授、专家等多角色评审。
- 评审流程和后台管理。

相比之下，本项目更偏向：

- 真实问答结束后的复盘。
- 真实问题和追问链的保存。
- 个人错误模式分析。
- 语音反思和重答训练。
- 跨场次的长期积累。

两者可以形成互补关系：

- 老师网站：让 AI 像评审一样提问。
- 本项目：让真实评审留下的问题变成学习资产。

### 2.5 竞争对比

| 维度 | 老师网站的实时评审 | 转写后复制给通用 AI | 本项目的目标 |
|---|---|---|---|
| 使用时机 | 汇报前或汇报中 | 事后一次性处理 | 事后持续复盘 |
| 主要输入 | 实时语音和汇报内容 | 用户手动复制的文本 | 录音、文字、用户反思和重答记录 |
| 主要输出 | 实时追问和评审意见 | 一次性总结 | 问题卡、缺口、复习队列和趋势 |
| 是否保留追问链 | 取决于具体产品设计 | 通常需要用户自己整理 | 作为核心数据结构保存 |
| 是否能跨场次比较 | 通常不是重点 | 很难自动完成 | 核心能力 |
| 是否能形成个人题库 | 通常不是重点 | 需要用户手工维护 | 自动积累 |
| 是否有重答训练 | 可能有模拟练习 | 需要用户另开对话 | 内置重答和前后对比 |
| 数据价值 | 练习数据 | 单次文本 | 个人问题资产和长期弱点图谱 |

### 2.6 产品必须赢在什么地方

不要和老师网站比“谁更像真实评审”，也不要和通用 AI 比“谁的模型更聪明”。要在一个明确维度上赢：

1. 从导入到形成问题卡的时间更短。
2. 问题、回答和追问链的还原更完整。
3. 回答缺口的描述更具体、更有证据。
4. 能跨场次发现重复问题。
5. 能把分析转成下一周的重答任务。

可以把这五点作为答辩时的产品价值主张。

### 2.7 老师系统“一次更新就覆盖”的风险

这个担心是合理的。如果老师系统同时增加：

- 历史记录保留。
- AI 总结。
- 个人问题总库。
- 评估结果和改进方案。

那么从功能清单上看，一个简单的复盘工具确实会被覆盖。

所以要区分两种竞争：

- 功能竞争：谁有录音、总结、题库和评估。
- 产品竞争：谁更适合某一类用户长期使用，谁的单位成本更低，谁的数据归用户所有。

老师平台的核心是评审和教学管理，本项目的核心应该是在校生自己的项目表达训练。即使两者都有“AI 总结”，用户的入口、数据归属和使用周期也不一样。

更稳妥的防守方式是：

1. 首版只服务“学生讲自己的软件项目”这一细分场景。
2. 把问题类型做成该场景专用的分类，而不是通用总结。
3. 让数据可导出、可迁移，强调用户拥有自己的问题库。
4. 支持本地模型或自带 API Key，降低长期使用成本。
5. 用跨场次复习和重答效果证明价值，而不是比功能数量。

如果老师平台未来也做这些功能，这不一定意味着项目失败。那时竞争点会变成：

- 谁更懂学生项目答辩。
- 谁的成本更低。
- 谁更愿意开放数据结构和模型选择。
- 谁更像长期训练工具，而不是一次性评审系统。

### 2.8 成本结构是产品优势，不只是工程问题

老师平台每个人限制 60 分钟，说明实时评审、实时语音和多角色 AI 的单位成本很高。持续运行、重复调用模型、长上下文和多人评审都会放大开销。

本项目不应该通过“送更多免费分钟”和它竞争，而应该改变成本结构：

- 以事后批处理为主，不做全程持续的 LLM 调用。
- 只在检测到问题时调用模型。
- 先做本地 ASR 或低成本 ASR，再做结构化分析。
- 将整场转写压缩为问题、回答、追问和少量上下文。
- 一次复盘使用有限次数的模型调用，而不是每个问题都重复读取全文。
- 使用小模型做分类，大模型只处理复杂推理。
- 缓存场次摘要、问题向量和已经生成的问题卡。
- 支持用户自带模型 Key 或本地模型，避免平台承担全部推理成本。
- 把“每次复盘的 token 预算”纳入产品指标。

因此，项目的差异化可以表述为：

> 不是更便宜地复制老师的实时评审，而是用异步、结构化和本地优先的方式，让学生能够长期、低成本地复盘。

## 3. 产品定位

### 3.1 推荐定位

“把每次面试或汇报中的真实问题，变成你的个人问题错题本。”

### 3.2 不做什么

- 不做实时打断式 AI 评审。
- 不做多角色评审大厅。
- 不承诺准确判断评审的心理。
- 不默认生成一段完美答案让用户背诵。
- 不把情绪识别当作核心能力。
- 不做大而全的会议助手。

### 3.3 核心设计原则

- 问题优先，不以整场会议为中心。
- 证据优先，所有判断尽量能回到原文和时间点。
- 用户可控，AI 的意图判断允许修改。
- 训练优先，每次分析都要产生行动。
- 隐私优先，录音和文本可以被删除、导出和本地保存。
- 长期优先，单次分析只是数据积累的入口。

### 3.4 首版场景：学生讲清楚自己的软件项目

首版不泛化到“所有面试”，而是聚焦一个可以自己反复验证的场景：

> 学生向老师、评审或面试官介绍自己做过的软件项目，并回答需求、技术、数据、测试、贡献、成本和风险相关问题。

这个场景适合作为第一个产品切口，原因是：

- 开发者自己就是目标用户，可以直接收集真实问题和样本。
- 软件项目答辩的问题类型相对稳定，容易形成分类。
- 学生通常缺少项目叙事和证据准备，痛点明显。
- 可以从课程项目、比赛项目、毕业设计和校招项目迁移。
- 与研发岗位面试有连续性，后续可以自然扩展。

首版问题地图：

| 维度 | 评审可能问什么 | 用户通常缺什么 |
|---|---|---|
| 需求与用户 | 为什么做这个项目？谁真正需要？ | 真实用户证据和需求来源 |
| 方案选择 | 为什么用这个技术方案？ | 替代方案、取舍和约束 |
| 架构与数据流 | 系统怎么运行？模块如何协作？ | 清晰的结构图和边界 |
| AI 必要性 | 为什么一定要用 AI？ | 传统方案对比和失败案例 |
| 数据与质量 | 数据从哪里来？如何验证？ | 数据来源、标注和评估指标 |
| 个人贡献 | 哪些部分是你做的？ | 贡献边界和具体产出 |
| 工程实现 | 怎么测试、部署和维护？ | 测试记录和工程证据 |
| 成本与性能 | 长期运行成本高不高？ | 成本模型和优化策略 |
| 风险与隐私 | 出错怎么办？数据怎么保护？ | 兜底方案和合规意识 |
| 反思与规划 | 最大不足是什么？下一步做什么？ | 诚实反思和可执行计划 |

这个表格可以直接变成首版的问题分析模板，也可以作为开源文档的一部分。

## 4. 核心使用闭环

### 4.1 流程

```mermaid
flowchart LR
    A[导入录音或文字] --> B[转写与角色区分]
    B --> C[提取问题、回答和追问链]
    C --> D[推断问题意图与考察点]
    D --> E[识别回答缺口和证据缺口]
    E --> F[生成问题卡]
    F --> G[语音反思]
    G --> H[重新回答]
    H --> I[前后对比]
    I --> J[进入复习队列]
    J --> K[跨场次趋势分析]
```

### 4.2 五个关键动作

1. 收集：导入录音、视频或文字，支持事后语音补充。
2. 拆解：识别提问、回答、追问和上下文。
3. 理解：指出可能的考察点、缺失证据和回答结构问题。
4. 重答：用语音重新回答，并比较前后变化。
5. 积累：形成个人问题库、高频弱点和每周复盘报告。

## 5. 问题卡数据结构

问题卡是整个产品的核心对象，所有 AI 分析都应落到这个结构上。

| 字段 | 说明 |
|---|---|
| `id` | 问题卡唯一标识 |
| `session_id` | 所属面试或汇报场次 |
| `question_text` | 原始问题文本 |
| `start_time` | 在录音中的开始时间 |
| `end_time` | 在录音中的结束时间 |
| `asker_role` | 提问者角色，如技术评审、业务评审、导师、HR |
| `context_summary` | 提问前的汇报上下文 |
| `follow_up_chain` | 相关追问链 |
| `intent_labels` | 可能的考察维度 |
| `intent_evidence` | 支持该判断的原文和时间点 |
| `original_answer` | 用户当时的回答 |
| `answer_summary` | 回答摘要 |
| `gap_labels` | 回答缺口类型 |
| `missing_evidence` | 缺失的数据、案例或项目证据 |
| `improved_outline` | 下一次回答的骨架 |
| `reflection_audio_url` | 用户事后语音反思 |
| `reflection_text` | 语音反思转写 |
| `retry_answers` | 重答记录 |
| `mastery_status` | 未理解、待重答、已掌握、反复出现 |
| `tags` | 岗位能力、项目、技术方向等标签 |

### 5.1 为什么要保存追问链

单个问题很容易被总结，追问链才更能暴露真实考察点。

例如：

- 第一问：为什么选这个方案？
- 第二问：你比较过哪些替代方案？
- 第三问：如果数据量扩大十倍，你的方案还成立吗？

这组追问说明评审关注的不是“介绍方案”，而是决策依据、替代方案和边界条件。把追问链保存下来，产品的信息价值会明显高于单轮问答总结。

## 6. AI 分析分类

### 6.1 问题意图分类

| 类型 | 示例问题 | 可能的考察点 |
|---|---|---|
| 证据核验 | 数据怎么来的？样本量多少？ | 数据可信度和严谨性 |
| 决策追问 | 为什么选这个方案？ | 决策依据和替代方案 |
| 贡献确认 | 这部分具体是你做的吗？ | 个人贡献和边界 |
| 风险意识 | 如果失败怎么办？ | 风险识别和兜底 |
| 深度测试 | 这个结论为什么成立？ | 底层逻辑和原理 |
| 反思能力 | 你最大的不足是什么？ | 复盘和学习能力 |
| 价值判断 | 这件事有什么意义？ | 影响、价值和目标 |
| 动机匹配 | 为什么选择这个岗位？ | 岗位理解与稳定性 |

### 6.2 回答缺口分类

| 类型 | 典型表现 |
|---|---|
| 没有结论 | 铺垫很长，直到最后才回答问题 |
| 没有证据 | 只有观点，没有数据、案例或结果 |
| 没有取舍 | 只说方案优点，没有比较替代方案 |
| 没有边界 | 不说明假设、限制和失败条件 |
| 贡献模糊 | 大量使用“我们”，不清楚个人做了什么 |
| 结构混乱 | 背景、行动、结果和反思混在一起 |
| 缺少反思 | 只讲成功，不讲失败和修正 |
| 表达过长 | 信息密度低，评审需要反复追问 |

### 6.3 AI 输出约束

- 不输出“评审一定认为你能力不足”这类心理断言。
- 输出“该问题可能在验证什么”以及对应证据。
- 所有意图判断必须能链接到原始文本或时间点。
- 不确定时显示“低置信度”或“需要用户确认”。
- 用户应能修改意图标签、缺口标签和掌握状态。

## 7. 语音反思助手

### 7.1 为什么语音优先

面试结束后，用户通常不想再写长文。语音录入可以降低复盘启动成本。

语音助手不是简单记录，而是根据本次内容提出少量追问：

- 哪个问题最出乎你的意料？
- 你当时卡住的原因是什么？
- 哪个项目证据你没有提前准备？
- 如果重新回答，你会先说什么？
- 这次表现中，你最想保留的一个动作是什么？

### 7.2 反思结果如何进入问题卡

AI 将语音反思拆成：

- 事实：当时发生了什么。
- 原因：为什么没有答好。
- 缺口：缺少什么证据或结构。
- 行动：下一次准备什么。
- 状态：用户自评的掌握程度。

这些内容自动关联到对应问题卡，而不是生成一份独立的会议总结。

### 7.3 重答模式

1. 随机抽取一个待复习问题。
2. 用户重新进行语音回答。
3. 系统转写并提取回答结构。
4. 对比第一次和第二次回答。
5. 比较结论是否更早、证据是否更具体、边界是否更清楚。
6. 更新掌握状态和下次复习时间。

不要把情绪识别作为评分依据。可以记录用户自评的紧张程度和信心，但不要从声音推断心理状态。

### 7.4 实时辅助面试：可以做，但不建议作为首版核心

技术上可以做成：

- 实时识别评审的问题。
- 判断问题类型。
- 快速给出回答提纲。
- 从用户已有的项目证据中检索可用材料。
- 在屏幕上显示关键词、结构提醒或追问预测。

但这个方向有几个明显风险：

- 很多面试和答辩明确禁止外部辅助，隐藏使用可能被视为作弊。
- 真实面试录音可能涉及对方隐私和知情同意。
- 实时语音、低延迟识别、问题判断和答案生成是四个不同的工程难题。
- 网络抖动或识别错误会在高压场合放大风险。
- 实时回答会鼓励用户依赖提示，削弱事后复盘和真正掌握。
- 单人两周内很难把实时链路做稳定，并把复盘闭环同时做好。

更稳妥的产品划分：

| 模式 | 使用场景 | 是否首版 |
|---|---|---|
| 事后复盘 | 真实面试或答辩结束后导入记录 | 是 |
| 模拟面试实时教练 | 自己练习时识别问题并给出结构提示 | 可作为增强功能 |
| 实际面试现场辅助 | 必须明确告知并获得允许，只提供问题记录、关键词和结构提醒 | 不作为首版核心 |

如果未来要做现场模式，也不建议做“隐藏式标准答案生成器”。更合理的边界是：

- 只记录问题，不替用户回答。
- 只提示回答结构，不生成完整话术。
- 只检索用户自己准备过的项目证据。
- 由用户确认是否开启，并明确告知使用方式。
- 面试规则禁止时直接关闭该功能。

首版应把“实时”留给模拟练习，把真实面试留在事后复盘。这样既降低伦理风险，也避免和老师平台的实时评审正面竞争。

## 9. 评估方案：和“复制给 AI”正面比较

### 9.1 基线方案

把同一份转写文本直接粘贴给通用 AI，提示词为：

> 请总结这次面试中的问题、我的回答和可以改进的地方。

### 9.2 产品方案

使用本项目的结构化流程：

- 自动切分问题与回答。
- 提取追问链。
- 生成问题卡。
- 标注意图和证据。
- 生成回答缺口。
- 进入复习和重答流程。

### 9.3 对比指标

| 指标 | 说明 |
|---|---|
| 问题召回率 | 真实问题中有多少被提取出来 |
| 追问链完整度 | 追问是否被正确关联到原问题 |
| 意图判断符合度 | 用户或人工评审是否认可该分类 |
| 缺口识别有用度 | 用户是否认为缺口指出了真正问题 |
| 到问题卡的时间 | 从导入到形成可复习问题卡所需时间 |
| 可行动性 | 是否产生下周可以执行的训练动作 |
| 跨场次价值 | 是否能发现重复问题和变化趋势 |

### 9.4 建议样本

- 5 到 10 段模拟面试或答辩录音。
- 20 到 50 个真实问题。
- 至少 3 类提问者角色。
- 至少 3 个重复出现的能力主题。

### 9.5 答辩时的关键实验

现场展示两条路径：

1. 把转写文本复制给通用 AI，得到一份总结。
2. 使用产品得到问题卡、追问链、缺口、反思和复习任务。

重点不是证明通用 AI 不行，而是证明：

> 通用 AI 能给出一次性答案，但本产品能把一次经历转成可重复使用的训练数据。

## 11. 角色分工

- 前端：一个主流程页面加问题卡详情页。

## 12. 技术方案

### 12.1 推荐架构

```text
Next.js 前端
    |
FastAPI 或 Next.js API
    |
Postgres + pgvector
    |
对象存储（录音、视频、反思音频）
    |
ASR + LLM + 结构化输出
```

### 12.2 推荐技术栈

- 前端：Next.js、Tailwind CSS。
- 后端：FastAPI 或 Next.js API Routes。
- 数据库：Postgres。
- 向量检索：pgvector。
- 文件存储：Supabase Storage 或兼容对象存储。
- 语音转写：faster-whisper 或云端 ASR。
- 结构化分析：Qwen、DeepSeek 等支持 JSON 输出的模型。
- 部署：Docker、GitHub Actions、Vercel 或云服务器。
- 测试：pytest、Playwright。

### 12.3 AI 流水线

1. 音频预处理和分段。
2. 转写和角色区分。
3. 问题和回答边界检测。
4. 追问链关联。
5. 意图分类。
6. 缺口分析。
7. 结构化 JSON 校验。
8. 低置信度标注和人工确认。
9. 保存问题卡和向量。
10. 生成复习任务。

### 12.4 结构化输出示例

```json
{
  "question_text": "你提到人机协作，能具体说明系统可靠性风险吗？",
  "asker_role": "技术评审",
  "intent_labels": ["风险意识", "深度测试"],
  "intent_evidence": [
    "追问要求说明可靠性风险",
    "问题与前一轮的人机关系回答直接相关"
  ],
  "answer_summary": "强调回退机制和人工接管",
  "missing_evidence": [
    "没有说明具体故障场景",
    "没有说明回退机制的触发条件",
    "没有说明人工接管后的验证方式"
  ],
  "confidence": 0.82
}
```

### 12.5 低 Token 成本设计

成本控制不能等到产品做完再优化，应该从第一版就写进架构。

推荐策略：

- 转写只做一次，保存结构化结果，不在后续分析中反复转写。
- 将一场面试压缩成“场次摘要 + 问题列表 + 相关上下文”，不把全文反复发给每个问题。
- 先做问题边界检测，再只对问题片段做意图和缺口分析。
- 对同一批问题使用一次批量结构化调用，而不是每个问题单独开一次长对话。
- 常见分类使用小模型或规则，复杂推理再使用大模型。
- 对重复问题使用向量检索，优先复用已有分析结果。
- 缓存用户的项目证据、回答骨架和历史标签。
- 对低置信度结果要求用户确认，避免错误结果反复触发重新分析。
- 设置单场次 token 预算和调用次数上限。
- 支持用户自带 API Key 和本地模型，给用户选择成本与隐私的权利。

建议把单场复盘的模型调用控制在 3 到 5 次主调用以内：

1. 转写或校对。
2. 问题与追问提取。
3. 批量意图与缺口分析。
4. 场次总结和复习任务。
5. 可选的用户反思整理。

这是一个设计目标，不是固定死线，最终应根据实际效果和成本测试调整。

### 12.6 性能与成本的平衡

- 事后复盘可以接受分钟级处理，不必为低延迟牺牲成本。
- 模拟面试需要秒级响应，应限制使用范围，不要默认全程调用大模型。
- 实时模式优先做本地语音活动检测和流式 ASR。
- 实时模式下只做问题检测、关键词和结构提示，不默认生成完整答案。
- 将处理任务放入异步队列，允许用户先离开，完成后通知。
- 在界面上显示本次处理的预估成本、实际 token 和耗时，培养用户的成本意识。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 只做转写和总结 | 容易被通用 AI 覆盖 | 强制以问题卡和复习闭环为核心 |
| 录音涉及隐私 | 用户不信任或存在合规风险 | 明确同意、加密、删除、导出和本地模式 |
| ASR 错误 | 问题提取和意图判断出错 | 保留原文时间点，允许人工编辑 |
| AI 过度推断 | 用户反感或误导 | 输出“可能考察点”并显示依据和置信度 |
| 两周范围过大 | 无法按时交付 | 只做一个主场景和一条完整闭环 |
| 模型成本过高 | 演示或开源使用困难 | 分段处理、缓存、设置长度限制、支持小模型 |
| 用户不愿复盘 | 数据不足 | 语音优先、3 分钟流程、自动生成下一步 |
| 与老师产品正面竞争 | 功能被覆盖 | 明确定位为事前/事中之外的事后复盘工具 |
| 老师平台增加历史记录和题库 | 功能清单被覆盖 | 聚焦学生项目答辩、低成本、可导出和跨场次复习 |
| 实际面试现场辅助 | 规则、隐私和伦理风险 | 只做模拟实时教练；现场模式必须披露且不生成隐藏答案 |

## 16. 演示脚本

### 16.1 五分钟演示流程

1. 打开一段模拟面试录音。
2. 系统自动转写并区分提问和回答。
3. 提取出 5 个问题和 2 条追问链。
4. 打开其中一张问题卡，展示可能的考察点。
5. 展示用户原回答和缺失证据。
6. 播放或录制一段语音反思。
7. 让用户重新回答同一个问题。
8. 对比两次回答的结论、证据和边界。
9. 打开复习页，展示高频弱点和下一次练习任务。

### 16.2 答辩时的核心话术

- 我们不是再做一个 AI 面试官，而是做面试后的学习闭环。
- 通用 AI 可以分析一次转写，但不会维护问题资产和复习状态。
- 我们不追求替用户生成完美答案，而是帮助用户发现问题。
- 我们的核心数据不是会议纪要，而是问题卡、追问链和回答缺口。
- 我们的评估基线就是“把同一份文本复制给通用 AI”，因此产品必须证明自己在结构化和长期复习上更强。

- 首版面向应届生和在校生。
- 首版优先解决“学生如何讲清楚自己的软件项目”。
- 产品需要长期使用，成本不能依赖持续的高价实时模型调用。
- 老师平台可能存在功能覆盖风险，因此不能只做通用转写和总结。
- 实际面试现场辅助存在规则和伦理风险，不作为首版核心。

### 17.2 仍需确认

1. 首版主要使用真实答辩录音，还是自己组织的模拟问答录音。
2. 用户是否愿意手动粘贴文字作为低成本备用入口。
3. 是否允许保存原始录音，默认保存多久。
4. 是否采用云端模型，是否需要本地模型模式。
5. 开源许可证选择 MIT 还是 Apache-2.0。
6. 是否已经有 5 到 10 份可用于测试的真实或模拟样本。
7. 首版是否需要加入“模拟面试实时提示”，还是完全放在第二轮迭代。

---

## 18. 一句话结论

“转写后复制给 AI”是必须承认的强基线，但它解决的是单次分析；本项目要解决的是长期复盘。

因此，项目的胜负点不是语音识别，也不是接一个大模型，而是：

> 能否把真实问题、追问链、回答缺口、语音反思和重答训练，组织成一个可持续使用的个人问题资产系统。

在单人、两周和长期低成本的约束下，最合理的首版不是“通用 AI 面试平台”，而是：

> 一个帮助学生讲清楚自己的软件项目、复盘评审问题并持续重答的项目答辩错题本。
